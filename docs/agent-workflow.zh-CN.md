# 可组合 Agent 工作流

[English](agent-workflow.md) | 中文

本文定义一套可公开、可组合的 Agent 工作流，把小而通用的公共核心与用户选择的主机和 Workspace 模块分开。它是一套决策框架，不要求模型公开隐藏思维链，也不要求每次回答前进行表演式停顿。

## 目标

- 保留用户真正的目标、授权边界和验收界面。
- 交付有证据的最简单完整方案，而不是最快给出貌似可行的回答。
- 让公共核心足够小，在不同语言、主机、工具和开发领域中都能成立。
- 只有用户理解影响和成本并选择后，才加入语言、工具、主机、实验、文档或领域行为。

## 行动前判断

开始非平凡操作前，Agent 只需在内部回答三个问题：

1. **第一性原理：** 用户需要什么结果，哪些是事实或推测，授权边界是什么，怎样观察成功？如果一个例子暴露了共性原因，应在多大相关范围内检查同类问题？
2. **奥卡姆剃刀：** 哪些成熟且持续维护的方案已经覆盖需求？直接采用、组合裁剪或聚焦的定制 MVP，哪个全生命周期复杂度最低？
3. **苏格拉底提问：** 什么薄弱前提、反例、失败模式或替代方案会改变拟定路径？

只有未决信息会实质影响架构、数据、权限、安全、兼容性、用户可见行为或授权时，才向用户提问。否则先检查现有证据，必要时说明低风险假设，然后继续。

“回答前停顿一下”应转化为上述内部检查，而不是增加固定等待时间或输出冗长推理过程。

## 指令分层

每一层只保存适合自己的内容：

- 全局 `~/.codex/AGENTS.md`：最小公共核心，加上这台主机明确选择的语言、报告、工具、平台和主机模块。
- 仓库或子目录 `AGENTS.md`：无法从项目中可靠发现的长期团队与代码库规则、命令和边界。
- 全局文件旁的选定 Markdown 规范：后端、前端或 Git 偏好，在相关工作时读取。参见[按需读取入口](global-agents.zh-CN.md#按需开发规范)。只要求审阅时给意见，要求简化时在授权范围内修改。
- 项目文档：项目原有的计划、设计记录、进度说明和 worklog；不要求固定目录结构。
- Skills：需要丰富说明、scripts、references、assets 或检查器的可重复流程。
- Memories 与会话索引：本机私有上下文。应提炼或建立索引，不把原始历史复制到公开仓库。

同一规则只保留一处权威说明。入口保留共同要求，条件性细节通过写明触发条件的链接按需读取；改写过时段落，删除重复解释。这适用于 `AGENTS.md`、规范和 Skill；参见 [writing for agents](https://github.com/mattpocock/skills/blob/main/skills/productivity/writing-for-agents/SKILL.md)。

一条常驻规则只有同时满足以下条件，才值得占用 instruction budget：在当前作用域长期稳定；难以或不值得每次重新发现；几乎每个任务都相关；遗漏后果明确。把 `/init` 和其他自动生成的 `AGENTS.md` 当作候选清单，而不是成品：仓库结构图、当前文件或 Service 位置、实现细节、当前进度、一次性纠正，以及可由代码搜索、manifest、子目录 `AGENTS.md`、项目文档或 Skill 按需披露的语言与领域流程，都应删除或迁移。审计旧规则时也使用同一准入标准，不因为某行“不冲突”就永久保留。参见 Codex 官方 [AGENTS.md 发现规则](https://learn.chatgpt.com/docs/agent-configuration/agents-md)和实用的[渐进式披露说明](https://www.aihero.dev/a-complete-guide-to-agents-md)。

### 从来源解决指令冲突

Skill 要求先访谈、创建文件、启动 subagent 或向外部写入时，先判断这些行为是否属于当前任务、是否已获授权。工作流建议不能覆盖用户明确要求，也不能增加权限。发生冲突时说明具体是哪条规则，不要默默停下、扩大任务，或把用户先前尚未改变的批准当作失效。系统、开发者指令和主机权限仍然适用。

反复冲突应改来源。例如，某个工具被定义为可选时，不应同时引入强制使用它的规则；触发过宽的 Skill 应缩小触发范围，或改成仅显式调用，而不是往全局核心里不断补反制条款。具体方法见 [Skill 选择与多主机使用](skill-management.zh-CN.md)。

OpenAI 的 [Astra 指南](https://developers.openai.com/api/docs/guides/latest-model#instruction-following)明确建议检查 Skills 和 `AGENTS.md` 中的冲突指令。这里采用的做法是明确范围、消除矛盾，不是禁用有用能力，也不是规定所有任务必须使用某个推理档位。改变模型默认设置前，应先用有代表性的任务比较效果。

### 仅在用户明确要求时使用子 Agent

[子 Agent 协作模块](../templates/optional/subagent-context.md)要求用户对当前任务或明确范围主动授权。普通任务请求不算授权。在已授权范围内，只传递新的任务说明，包括目标、必要事实或文件入口、允许操作、写入分工和预期结果。主 Agent 仍负责综合、集成和最终完成。

### 把 session 所在位置当作线索

维护私有 session 归档时，不要只凭 `cwd` 判定项目归属。应同时参考相关 Git 根目录、实际修改的路径或产物、用户明确表达的目标，以及记录属于根线程、fork 还是 subagent。一次 session 可能跨越多个项目，也可能只是个人运维；subagent 复制的上下文不能证明其中提到的每个项目都真的发生了修改。原始映射应保持私有，只公开经过提炼且能跨项目复用的经验。

## 一个全局入口，渐进记录项目

通常只配置主机全局 `AGENTS.md`。它保存最小公共行为和明确选择的主机偏好，不保存项目状态、会话历史或私有主机清单。

重要阶段完成后，全局规则可以加载 `organized-proj`。Skill 检查所属项目，只更新现有且相关的记录；不安装项目工作流，也不强制目录结构。小改动不记录。`templates/workspace/` 下的实验、Robotics、UI 和 worklog 参考仅在当前任务需要时加载。

安装选项见[主机全局 AGENTS 规则解读](global-agents.zh-CN.md)，阶段收尾行为见[渐进式项目记录](workspace-continuous-documentation.zh-CN.md)。

### 选择模块，而不是默认继承

跨平台核心不携带个人语言、worktree、subagent、时区或领域策略。安装时，Agent 先检查主机和现有规则，排除不相关模块，再解释剩余选项，让用户选择。

- 明显不相关的模块不要拿来逐项提问。主机里存在 Robotics 仓库，不代表普通 Web workspace 也需要 Robotics 规则。
- 一个选项不能自动推导另一个。选择中文不等于选择记录时区；选择持续文档也不等于选择实验或 Robotics 规则。
- 已选模块只能出现一次；时区等参数化模块不得保留未替换占位符。

机器路径、版本快照、凭据、session 状态和主机清单不得进入公开模块。

## 公共核心与可选默认值

最小核心只保留在大多数开发场景都成立的行为：独立判断、授权与秘密边界、聚焦实现、证据驱动调试、兼容性决策、风险成比例验证和坦诚汇报。

以下内容属于显式选项，不是通用默认值：

- 对话语言和 English 技术标识的处理方式；
- 只有用户明确授权后才使用子 Agent，并使用新上下文和清晰写入边界；
- 除非用户明确要求，否则不使用 Git worktree；
- 工作记录使用的时区；
- 更严格的 Git 仓库保护；
- 按需加载的实验纪律、Robotics 验证及其他领域流程。

选项目录位于 [templates/optional/](../templates/optional/)，项目选项位于 [templates/workspace/](../templates/workspace/)。模块文件只保留选中后真正执行的指令；选择条件、前提和取舍留在本文与部署解读中。部署 Agent 应只推荐少量相关模块，用通俗语言解释，并通过拟议 diff 获得用户批准。

## 兼容性必须经过决策

不要条件反射式保留兼容，也不要条件反射式破坏兼容。

| 场景 | 默认方向 | 需要确认的证据 |
| --- | --- | --- |
| 个人科研、原型、未发布实验 | 倾向直接迁移并移除旧路径 | 现有消费者、复现实验需求、回滚成本 |
| 实验室公共基础设施、多人工具、公开包、工业或生产系统 | 倾向有边界的兼容或迁移方案 | 支持版本、下游用户、弃用周期、回滚与可观测性 |
| 场景不明确，或选择会改变架构与用户行为 | 询问开发者 | 具体消费者、必须维持的契约、可接受的破坏范围 |

必须兼容时，优先给出明确的版本边界、迁移路径和移除条件，避免永久 fallback 与静默双行为。

## 实现纪律

- 选择能完整满足当前需求且全生命周期复杂度最低的路径。“简单”看全生命周期成本，不只是 diff 更小。
- 建设重要基础设施前，先搜索少量成熟且持续维护的开源方案，比较直接采用、组合或裁剪，以及聚焦的定制 MVP。选择实质影响架构、依赖或长期维护责任时，把具体选项和推荐交给用户决定。即使最终更适合定制实现，也要复用已经验证的接口和运维模式。
- 只实现用户要求的行为，不顺手增加相邻功能、未来扩展点或解释性脚手架。删除未要求的工作时，也删除它留下的叙事残渣：名称、注释、测试、commit 和 PR 摘要应描述实际交付，不应宣传本来就无关的省略项。
- 这适用于所有交付界面，包括 UI、帮助和文档，不只是 PR。用户可见文案应解释产品，不复述开发 Prompt，也不展示 Agent 内部约束。
- 把文件长度、圈复杂度、嵌套深度和依赖数量当作审查信号，而不是全局硬 gate。项目已有并明确负责的限制可以执行，但不要新增只会把同一责任拆成更多文件或 wrapper 的统一阈值。
- 默认不新增 hash、冻结 contract、baseline、gate、影子状态或自制校验。先说明它要防止的具体事故，以及 Git、版本号、主键、事务、唯一约束、类型或普通定向测试为什么不足。保留已有安全措施；认证、数据安全、不可逆操作、正式发布和其他已经证明的高风险边界仍使用更严格控制。
- 遇到非显然问题时，先用证据定位被破坏的责任、约束、不变量或数据流，再选择修复方案；用最小精确修改恢复正确模型，不为保持小 diff 叠加临时补丁。
- 在已工作的系统上逐层增长。每层先端到端验证，再增加下一项能力。
- 保持关注点分离，但不要添加推测性的抽象、配置或扩展点。
- 保护无关工作；每个修改文件和修改行都应能追溯到需求或当前变更引发的必要修复。
- 生产代码中不保留 debug 产物、死代码、过期分支和任务临时文件。
- 倾向长期可靠的架构选择，但不要在当前验收标准达成前建设想象中的未来。

任务涉及多台主机、多个项目或多项产出时，结束前逐一核对；完成一个目标不代表其余目标也已完成。清单留在当前任务或已有 plan，不额外创建全局 registry。前置条件失败时，区分授权问题、持续故障和临时状态；若时效性事实决定能否继续，应重新确认，不能把旧资源快照或一次网络失败变成无限期阻塞。

## 为交付服务的验证

先定义公开行为和可观察结果，再选择能暴露重要故障的最小真实检查。优先通过真实用户或调用方入口验证。命令成功或贴着实现写出的断言，如果没有观察到用户要求的结果，就不能作为完成证据。

复用已有检查，相关证据足够就停止。检查失败时，区分产品回归、过期断言、环境问题和原有无关故障。不能为了迁就检查器改变正确行为，也不能为此新建测试基础设施；剩余的重要限制如实报告。

对于 UI、图件、文档和文字，修复明显技术问题后交付实际产物供用户检阅。展示和表达是否满意由用户决定。不要为临时措辞、元素位置、图件选择或排版写单元测试和永久断言。

只有确实影响共享逻辑、认证、数据安全、不可逆操作或发布时，才提高验证强度。这是风险判断，不是固定测试数量、覆盖率配额或默认全量测试仪式。

## 渐进式项目记录

重要阶段结束时，检查项目已有文档，只更新本次工作影响的权威记录。把已验证结果、长期设计变化、未解决风险和下一步写回项目原有位置。不要为了满足工作流而新建固定的 `active`、`design` 或 `worklog` 目录。小改动以及没有长期结果的任务无需阶段记录。

## Skill 打包门槛

流程能写成 Skill，不代表应该立刻写成 Skill。只有同时满足以下条件才打包：

- 触发条件和预期输出稳定；
- 会跨任务或跨项目重复；
- 渐进加载确有价值；
- scripts、references、assets 或自动检查能带来实际收益；
- 安装、更新和生成状态的成本低于流程节省的成本。

meta-skill 或 Skill 框架可以帮助编写与评测，但它自己的 benchmark 只能作为候选证据。安装前应检查代码、依赖、生成文件、上下文占用和可复现性。

## 更新本工作流

只有出现反复反馈、已纠正假设、重复故障或已验证的工具/平台变化时，才修改稳定规则。广泛适用的行为进入核心；用户、工具、主机、平台和领域选择进入具名模块。一次性偏好和机器状态不进入公开规范。中英文语义发生变化时，应在同一次修改中同步更新。

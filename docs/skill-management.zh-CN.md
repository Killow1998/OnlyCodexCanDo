# Skill 选择与多主机使用

[English](skill-management.md) | 中文

统一 Skill，应该统一来源、版本和选择方法，而不是让每台电脑安装同一大包。先让有用的 Skill 在需要它的地方出现，再处理自动更新。

## 先分清三件事

| 状态 | 含义 | 不能据此推断什么 |
| --- | --- | --- |
| 磁盘上已安装 | 文件存在 | 不代表当前会话发现或使用了它 |
| 当前会话可发现 | 名称、描述等进入候选列表 | 不代表完整正文已经加载 |
| 本次任务已使用 | Agent 读取正文并按需使用资源 | 不代表它提高了质量，也不代表所有脚本都运行过 |

Codex 本身已经按“先名称和描述、需要时再读正文”的方式渐进加载。大量描述仍有选择成本；触发过宽的 Skill 也可能被频繁加载。因此，精简目录与缩小触发条件解决的是不同问题。[官方说明](https://learn.chatgpt.com/docs/build-skills)

## 按用途选择，不按数量评价

| 选择 | 适合什么 | 例子 |
| --- | --- | --- |
| 跨项目可发现 | 多数项目都可能需要，触发准确 | 文档格式处理、明确范围的官方资料查询 |
| 仅项目可发现 | 依赖项目环境、领域或团队约定 | 仿真验证、某个框架的调试工具 |
| 仅显式调用 | 有价值，但会明显改变工作方式 | 深度访谈、TDD 教练、全仓库重构审查 |
| 暂停使用 | 触发错误、规则冲突、依赖缺失，或收益尚不明确 | 等待修订和验证的试用 Skill |

“最近没有用到”不是删除理由；低频但重要的能力可以按需保留。正文很长也不必直接删除，应先看它是否真的被加载、能否把细节移到按需引用的资源。

## 三种现成手段

### 暂停而不删除

当前 Codex 官方支持在用户 `config.toml` 中按实际 `SKILL.md` 路径禁用，配置后重启：

```toml
[[skills.config]]
path = "/absolute/path/to/example-skill/SKILL.md"
enabled = false
```

部署时使用目标主机真实路径，并保留原配置。不要靠移动整棵技能目录或删除插件缓存来做开关。[配置说明](https://learn.chatgpt.com/docs/build-skills#enable-or-disable-local-codex-skills)

### 只在点名时调用

可维护的 Skill 可以在自身 `agents/openai.yaml` 中选择：

```yaml
policy:
  allow_implicit_invocation: false
```

这与禁用不同：它仍可显式调用。不要假定其他工具的同名或相似 frontmatter 字段在 Codex 中等价生效；先核对当前版本。修改第三方 Skill 时保留来源和本地修改记录，避免更新覆盖。[调用策略](https://learn.chatgpt.com/docs/build-skills#optional-metadata)

### 只给需要的项目一个入口

把源文件保留在普通、非自动发现的目录，只在选中的 workspace 的 `.agents/skills/` 中建立该 Skill 文件夹的符号链接。Codex 支持跟随 Skill 文件夹符号链接；链接目标必须在该主机上可读。Windows 还需验证链接创建权限。[发现位置](https://learn.chatgpt.com/docs/build-skills#where-to-save-skills)

如果同一份 Skill 仍在用户全局发现目录里，另加项目链接并不能把它变成项目专用。不要让同名旧副本和新入口同时参与发现；先比较内容，再批准迁移。绝对路径链接不适合原样提交给其他机器，公开仓库保留部署说明或相对、可移植的来源。

## 一次有边界的审查

1. **盘点实际入口。** 查看全局、项目、插件和旧安装目录，以及禁用配置；记录来源、版本或文件摘要、调用策略和依赖。不要只数 `SKILL.md`。
2. **抽样看真实任务。** 区分用户主会话、fork 和 subagent，说明全文或片段覆盖。去除继承历史的重复，区分 Agent 转发指令和用户直接反馈；标日期前核对导入或重放时间戳。引用的博客或重复规则不能证明 Agent 真犯过相应错误，文件名、引用和安装记录也不算成功使用证据。
3. **找具体成本。** 是否无故提问、增加另一套计划文档、强制 subagent、重复检查，或者把“审查”变成发布 Issue、提交或远端写入？同时记录它真正帮助完成了什么。
4. **每项给一个处理意见。** 保留、限项目、显式调用、修订或暂停。指出理由和未验证部分，不因为另一个人推荐就全量安装。
5. **小范围验收。** 重开会话检查实际列表；用一个匹配任务与一个不该触发的请求核对路由；再看真实工作是否更少返工、更少多余产物。文件一致只证明同步成功，不证明能力有效。

## 多台主机怎样保持一致

共享 Skill 的来源与经过验证的版本，主机私下记录自己选择了哪些入口和本地例外。同一个任务型 Skill 尽量使用同一来源；平台工具、领域模块和个人称呼不必相同。先在一台主机验证，再按授权范围更新其他主机。

同步前比较本地修改，升级后检查引用、依赖和实际触发。按需升级，不要求每次工作前在线检查。不要同步整个 `.codex`：会话、凭据、数据库、缓存和插件运行状态都不是 Skill 源码。插件由对应的管理机制更新，不手改其缓存。

若只是几份自用 Skill，来源清单和项目链接通常已够用；需要向他人稳定分发或一起交付连接器时，再考虑插件打包。不要为了统一而先造一个新的管理平台。

## 可直接使用的只读审查 Prompt

```text
只读审查当前主机实际使用的 AGENTS.md、引用规则和已选 Skills，找出会造成重复提问、意外停工、扩大任务或交付不完整的矛盾与重叠。
先核对实际发现范围与启用状态；有代表性会话时可以抽样，但说明覆盖范围，不把已安装或曾被引用当作有效使用。
重点检查自主性、澄清、批准、任务完成和验证停止条件。区分有意设置的保障与无意增加的流程；先前已批准且没有变化的决定不应反复询问。
每项输出：文件与原句、可能影响、具体替换建议、是否改变权限。保留明确的批准要求；建议扩大权限时单独指出，不直接应用。
按实际影响排序，不凑问题数量；有益的规则和证据不足的疑点也应区分。先给我可审阅建议，不修改配置、文件、会话标题或外部状态。私有会话和主机信息不要放进公开仓库。
```

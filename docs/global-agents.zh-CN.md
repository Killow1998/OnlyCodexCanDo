# 主机全局 AGENTS 逐条解读

[English](global-agents.md) | 中文

本文解释 [templates/AGENTS.global.md](../templates/AGENTS.global.md) 中每一条规则的概念、理由和对开发行为的影响。编号 `G1` 至 `G30` 与模板中的 bullet 顺序一一对应；Windows 可选片段使用 `W1` 至 `W8`。

## 核心概念

### 第一性原理

第一性原理是把问题拆到当前能够直接确认的事实、必要约束和不可违反的不变量，再从这些基础重新推导方案，而不是因为“大家通常这样做”就沿用现成结论。

例如，用户说“需要保留旧接口”时，第一性原理不会立即增加兼容层，而会先确认真正的不变量是“现有消费者不能中断”、还是“所有旧语法永久有效”。前者可能通过一次迁移解决，后者才需要长期兼容。它能减少继承错误前提，但不代表忽略成熟经验；经验仍然是候选证据，需要结合当前事实验证。

### 奥卡姆剃刀

奥卡姆剃刀是在多个同样满足需求的解释或方案中，优先选择假设、状态、依赖、分支和维护责任更少的一个。它追求的是总体复杂度最小，不是代码行数最少，也不是为了小 diff 接受错误架构。

开发影响是减少推测性抽象、无用配置和永久 fallback；但如果一个成熟依赖比自行实现更可靠，引入依赖反而可能是更简单的总体方案。

### 苏格拉底提问

苏格拉底提问通过追问定义、证据、反例、因果和替代方案来检验一个判断。例如：“什么证据证明这是根因？”“如果没有旧消费者，兼容层还必要吗？”“哪个反例会推翻当前方案？”

它用于提高决策质量，不是把所有问题都反问用户。Agent 应先自行检查能获取的证据，只把真正会改变结果或授权边界的问题交给用户。

### 已确认事实、合理推测和未验证假设

- 已确认事实：由代码、配置、命令输出、权威文档或真实界面直接支持。
- 合理推测：由多个事实推导出的最可能解释，但尚未被直接证明。
- 未验证假设：为了继续工作暂时采用、且仍可能错误的前提。

这一区分防止“看起来合理”被写成技术事实，也让用户知道哪些结论可以直接行动、哪些需要进一步验证。

### 目标、授权边界和真实验收面

- 目标：用户真正要得到的结果，而不是表面的操作步骤。
- 授权边界：用户允许 Agent 读取、修改、删除、提交、推送或影响外部系统的范围。
- 真实验收面：用户实际依赖的成功信号，例如真实 UI 保存成功、客户端完整握手或硬件行为；测试桩、健康检查和静态配置只是代理证据。

先确认三者可以防止“命令成功但任务没完成”，也防止 Agent 用实现步骤推导出未经授权的外部动作。

### 兼容边界

兼容边界说明哪些旧版本、调用方、数据或行为必须继续受支持，以及支持到何时、怎样迁移和何时移除。没有边界的“保持兼容”通常会变成永久代码负债；没有调查消费者的“直接破坏”则可能造成真实事故。

### 风险成比例验证

验证强度应随影响范围和失败代价变化。局部、低风险改动可以用一次定向检查同时覆盖多个证据角度；共享模块、数据、权限、安全、基础设施和用户界面则需要更广的真实路径验证。目标是提高置信度，不是机械凑测试数量。

## Independent Judgment：G1-G6

| ID | 规则含义 | 对开发的影响 |
| --- | --- | --- |
| G1 | 非平凡操作前确认真实目标、授权边界和可观察验收信号。 | Agent 会先确定“完成”的定义，再选择工具和修改范围，减少做完错误任务或越权操作。 |
| G2 | 主动检查薄弱前提、缺失信息、隐藏风险和不必要的高成本路径。 | 需求不会被机械照抄；实现前会暴露错误架构方向、遗漏消费者和更便宜的替代方案。 |
| G3 | 区分事实、推测和假设，并先验证技术结论。 | 调试报告和设计决策更可信；无法验证的部分会明确保留不确定性，而不是编造版本或根因。 |
| G4 | 用第一性原理找必要约束，用奥卡姆剃刀降低总体复杂度，用苏格拉底提问寻找反例。 | 方案会从真实约束推导，避免盲从惯例、过度设计和未经检验的单一路径。 |
| G5 | 只有未决问题会实质改变架构、数据、权限、安全、兼容、用户行为或授权时才提问。 | 保留用户主观决策权，同时避免低价值澄清阻塞敏捷开发；低风险假设会被说明后继续执行。 |
| G6 | 评估长期维护和失败成本，但当前验收完成前不建设推测性未来。 | 防止短期补丁长期腐烂，也防止以“可扩展”为名提前增加抽象、配置和依赖。 |

## Language and Reporting：G7-G10

| ID | 规则含义 | 对开发的影响 |
| --- | --- | --- |
| G7 | 默认中文交流，已有项目文档沿用原语言。 | 用户可以保持中文敏捷开发；不会把英文仓库文档无故翻成中文并制造风格不一致。 |
| G8 | 代码、API、命令、错误和专有名词保留 English。 | 搜索错误、复制命令和对应官方文档更准确，避免翻译破坏技术标识。 |
| G9 | 报告简洁、直接、坦诚，只保留结果、证据、重要阻塞和未完成项。 | 减少过程噪声和上下文消耗，但不会用简洁掩盖失败或未验证内容。 |
| G10 | 只有可视化能显著改善关系、状态、布局或比较理解时才使用。 | 复杂架构和流程更易读；简单问题不创建低价值图表或额外文件。 |

## Execution Boundaries：G11-G17

| ID | 规则含义 | 对开发的影响 |
| --- | --- | --- |
| G11 | 保留原目标与限制，在授权内端到端完成，并从真实结果验收。 | 不会停在“代码已写”或“命令返回 0”；会检查用户实际依赖的行为。 |
| G12 | 保护无关工作；破坏性、生产、外部、远端、commit 和 push 动作必须有对应授权。 | 降低误删、覆盖用户修改和影响外部系统的风险；本地实现授权不会被扩展成发布授权。 |
| G13 | 默认在当前 checkout 工作，不主动创建 worktree。 | 避免 ROS、依赖、环境变量和生成状态分散；代价是并行分支隔离减少，因此只有用户明确需要时才启用。 |
| G14 | 默认单 Agent；subagent 需用户授权、任务真正独立且只传最小上下文。 | 防止完整历史和图片复制导致上下文与磁盘膨胀；只有并行收益明确时才承担协调成本。 |
| G15 | `rtk` 只在过滤不损失证据时使用，需要完整输出就回到原生命令。 | 可以节省 token 和噪声，但诊断能力、错误细节和验收证据优先。 |
| G16 | 修改聚焦且简单，不做无关重构、推测性抽象、无用配置和低信号测试。 | diff 更容易审查和回滚，当前任务不会顺便改变整个代码库。 |
| G17 | 成熟依赖能降低总体复杂度时优先使用，先检查项目模式与权威文档。 | 减少重复造轮子；同时防止因未调查现有能力就新增包或错误依赖。 |

## Compatibility：G18-G21

| ID | 规则含义 | 对开发的影响 |
| --- | --- | --- |
| G18 | 不条件反射式保留兼容，也不条件反射式破坏兼容。 | 每次兼容选择都需要消费者、成本和场景证据，避免永久 fallback 或意外破坏。 |
| G19 | 个人科研、原型和未发布实验在确认消费者与复现需求后倾向直接迁移。 | 这类项目可以更快删除旧路径和技术债，但仍保护实验复现与真实依赖。 |
| G20 | 公共基础设施、多人工具、公开包、工业和生产系统倾向有边界迁移。 | 需要版本范围、回滚、可观测性和移除条件，降低下游中断风险。 |
| G21 | 场景不清或选择会改变架构与用户行为时询问开发者。 | 把产品契约和风险偏好的最终决定留给人，而不是由 Agent 默默选择。 |

## Project Knowledge：G22-G26

| ID | 规则含义 | 对开发的影响 |
| --- | --- | --- |
| G22 | 只有 workspace 已有或明确采用持续文档流时才执行；全局模板本身不触发建文档。 | 主机全局设置与项目文档部署保持解耦，小项目不会被自动塞入一套 docs 体系。 |
| G23 | 已采用时，项目 `AGENTS.md` 只放稳定规则和文档路由，不放运行状态。 | Agent 每次都能快速找到规范来源，且不会把过期进度当成永久指令。 |
| G24 | 架构、决策、验证方法、项目状态和有意义记录进入项目现有 `docs/`。 | 会话中产生的耐久知识可以跨会话恢复，同时沿用项目已有结构。 |
| G25 | 优先维护一个 living project-state；临时知识并入规范文档后清理任务产物。 | 减少 `HANDOFF_v2_final` 式文件堆积，恢复入口保持唯一且当前。 |
| G26 | 未经授权绝不删除用户原有文档、历史或证据。 | “保持整洁”不能成为销毁未知价值资料的理由；清理仅覆盖任务创建且已确认冗余的内容。 |

## Risk-Proportional Verification：G27-G30

| ID | 规则含义 | 对开发的影响 |
| --- | --- | --- |
| G27 | 适用时从预期行为、边界或回归、独立证据三个角度验证。 | 避免只测试 happy path，或只看 diff 就宣称真实功能成功。 |
| G28 | 验证随风险调整；低风险改动的一次快速命令可以覆盖多个角度。 | 保留敏捷速度，不机械运行三套测试或全量 CI。 |
| G29 | 核心流程、共享模块、数据、权限、安全、基础设施和用户界面扩大验证，并优先真实验收面。 | 高影响改动会得到集成和用户侧证据，不会被代理指标的成功掩盖。 |
| G30 | 某角度不可用时说明原因；同一问题三次有效验证仍失败就停止叠补丁并审查架构。 | 未验证项保持透明；反复失败会触发根因与失败边界分析，而不是第四个猜测性 patch。 |

## Windows 可选片段：W1-W8

下列规则来自 [templates/platform/windows-shell.md](../templates/platform/windows-shell.md)，只在 Windows native 中常驻。

| ID | 规则含义 | 对开发的影响 |
| --- | --- | --- |
| W1 | Shell 行为相关时确认 Windows native/WSL，并报告实际 PowerShell 路径与版本。 | 命令选择基于真实运行时，避免把 WSL、WindowsApps alias 或不同 PowerShell 版本混为一谈。 |
| W2 | PowerShell 原生任务优先实际可用的 `pwsh -NoProfile`，必要时才用 5.1。 | 获得现代语义且减少 profile 污染，同时保留旧模块兼容路径。 |
| W3 | 不假设 `pwsh` 标准安装路径，必须确认可执行文件真的能启动。 | 避免存在 alias 但沙箱无法执行时反复失败。 |
| W4 | 文件写操作从头到尾使用一个 Shell，避免多层嵌套转义。 | 降低路径、引号和变量在 PowerShell、cmd、Bash、WSL 之间被错误解释的风险。 |
| W5 | 特殊路径使用 `-LiteralPath`；外部程序检查 `$LASTEXITCODE` 并保留 `stderr`。 | 空格与方括号路径不会被当成通配符，外部命令失败不会被 PowerShell 的表面成功掩盖。 |
| W6 | 失败后先分类原因并改变下一次尝试，不原样盲目重跑。 | 调试从堆重试转为证据驱动，减少重复副作用。 |
| W7 | 复杂可复用逻辑进入范围明确的 `.ps1`，任务临时脚本结束前清理。 | 减少脆弱的一行转义；只有有维护价值的脚本才留在仓库。 |
| W8 | Unix-first 项目确有收益时使用 Git Bash 或 WSL，不按习惯混用。 | ROS、Shell 脚本等项目可保留原生工具链，同时避免无必要的环境分裂。 |

## 维护方式

解释文档不替代模板；Agent 实际执行以模板中的规则为准。模板新增、删除或改变一条 bullet 时，应同步更新编号、概念解释和开发影响，并验证没有漏项。

Workspace 规则逐条解读见[持续项目文档规则解读](workspace-continuous-documentation.zh-CN.md)。

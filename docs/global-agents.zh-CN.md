# 主机全局 AGENTS 核心与选项解读

[English](global-agents.md) | 中文

本文解释 [templates/AGENTS.global.md](../templates/AGENTS.global.md) 最小核心，以及 [templates/optional/](../templates/optional/) 和 [templates/platform/](../templates/platform/) 中各选项会怎样影响开发。公共核心广泛适用；其他模块都必须先说明行为和取舍，再由用户明确选择。

## 公共核心背后的概念

### 第一性原理

第一性原理把问题拆到当前能够直接确认的事实、必要约束和不可违反的不变量，再从这些基础重新推导方案，而不是因为“大家通常这样做”就沿用结论。成熟经验仍是候选证据，不是不可质疑的前提。

### 奥卡姆剃刀

在多个同样满足需求的方案中，奥卡姆剃刀优先选择假设、状态、依赖、分支和维护责任更少的一个。它追求总体复杂度最小，不是代码行数最少，也不支持为了小 diff 接受错误模型。

### 苏格拉底提问

苏格拉底提问通过定义、证据、反例、因果和替代方案检验判断。它不应把每个任务变成问卷：Agent 先检查现有证据，只把会实质改变结果或授权的选择交给用户。

### 事实、推测、假设与验收

- 已确认事实：由代码、配置、命令输出、权威文档或真实界面直接支持。
- 合理推测：从事实推导出的最可能解释，但还没有直接证明。
- 未验证假设：为了继续工作暂时采用、仍可能错误的前提。
- 真实验收面：用户实际依赖的成功信号，而不是方便执行的健康检查或静态代理指标。

### 兼容与验证边界

兼容边界说明哪些消费者、版本、数据或行为继续受支持、如何迁移以及何时结束。验证强度则随影响范围和失败代价变化。永久兼容和三套全量测试都不是通用默认值。

## 最小公共核心规则

| 核心规则 | 对开发的影响 |
| --- | --- |
| 非平凡操作前确认真实目标、授权边界和可观察验收信号。 | 工具和范围服从明确的完成标准，减少做完错误任务或越权操作。 |
| 检查薄弱前提，并区分事实、合理推测和未验证假设。 | 看似合理的解释不会变成编造的技术事实；更便宜或安全的替代路径会在实施前出现。 |
| 使用第一性原理、奥卡姆剃刀和苏格拉底反例。 | 设计服从必要约束和总体复杂度，而不是习惯、行数或未经挑战的单一路径。 |
| 只有未决事项会实质改变架构、数据、权限、安全、兼容、用户行为或授权时才提问。 | 用户保留重要决定权，同时不让低价值澄清阻塞敏捷开发。 |
| 考虑维护和失败成本，但不提前建设推测性未来。 | 同时避免会腐烂的临时补丁和过早扩展。 |
| 保留原目标，并把已授权工作推进到真实结果验证。 | Agent 不会在“代码写完”或退出码为零时停止，而会检查用户真正依赖的行为。 |
| 保护无关工作；破坏性、生产、外部、远端、commit 和 push 动作需要对应授权；秘密和私有运行状态不进入共享输出。 | 本地实现授权不会默默扩展为数据损失、发布或凭据泄露。 |
| 选择完整满足需求的最简单聚焦修改。 | diff 容易审查，避免无关重构、推测性抽象、无用配置和低信号测试。 |
| 非显然问题先定位被破坏的责任、约束、不变量或数据流。 | 根因分析发生在叠补丁之前，修复仍限定在恢复正确模型所需范围。 |
| 失败后先分类原因并改变下一次尝试，不盲目重复。 | 调试能得到新证据，并避免重复副作用。 |
| 根据消费者、复现需求、失败成本和迁移证据决定兼容；选择影响重大时询问。 | 同时防止永久 fallback 债务和意外破坏。 |
| 重大架构、依赖、权限、安全或用户行为变更前，检查项目模式和权威文档。 | 减少重复造轮子和基于过期或想象中的框架行为做决定。 |
| 任务结束前清理本次创建的 debug 和临时产物，除非它们成为正式资产。 | 保持 Workspace 整洁，同时不删除用户原有资料。 |
| 适用时从预期行为、相关边界或回归、独立证据三个方向寻找验证。 | 验证不会只覆盖 happy path，也不会只看 diff 就宣称成功。 |
| 验证强度随风险变化。 | 低风险修改保持快速；高影响修改获得集成、界面、数据或基础设施证据。 |
| 优先真实验收面，并说明无法取得或不适用的证据。 | 代理指标不能代替用户实际使用的行为，剩余不确定性保持可见。 |
| 三次有意义的修复与验证仍失败时，审查架构和故障边界。 | 重复失败触发模型复查而不是第四次猜测。 |
| 简洁、直接、坦诚地报告结果、证据、阻塞、不确定性和未完成项。 | 用户得到有助于决策的信息，不被过程噪声或隐藏失败干扰。 |
| 只有可视化能明显改善理解时才使用。 | 复杂关系更清楚，简单任务不产生低价值图表和产物。 |

## 可选主机模块

“可选”不代表价值低，而是说明该规则表达个人偏好、依赖某种工具或运行环境，或者带有并非人人需要的成本。

| 模块 | 增加的行为 | 选择问题与取舍 |
| --- | --- | --- |
| [中文优先](../templates/optional/chinese-first.md) | 对话和说明使用中文，技术标识保留 English。 | 用户是否希望中文成为日常工作语言？它能提高中文用户流畅度，但不应成为公开通用默认值。 |
| [单 Agent 默认](../templates/optional/single-agent.md) | 默认单 Agent；subagent 需要明确授权、任务独立并限制上下文。 | 用户是否更重视减少上下文复制和协调成本，而不是自动并行？ |
| [当前 checkout 工作](../templates/optional/no-worktrees.md) | 除非用户要求，否则不使用 Git worktree。 | 环境集中是否比并行分支隔离更重要？ROS、硬件、生成状态或需要手动 source 的环境通常更相关。 |
| [RTK](../templates/optional/rtk.md) | 选择性过滤输出，需要完整证据时回到原生命令。 | RTK 是否已安装？用户是否接受过滤可能隐藏细节？节省 token 不能降低诊断能力。 |
| [记录时区](../templates/optional/timezone.md) | Agent 创建的 worklog 和实验记录使用选定 IANA 时区，同时保留来源时间。 | 记录应使用哪个时区？安装前必须替换占位符。 |
| [仓库安全](../templates/optional/repository-safety.md) | 写入前检查 branch/status，严格保护无关修改，维护仓库边界并要求显式 Git 发布授权。 | 这台主机是否经常修改 Git 仓库，并值得承担更严格的操作检查？ |
| [数据迁移安全](../templates/optional/data-migration-safety.md) | Schema 和持久数据修改前说明目标、风险、回滚，并验证真实消费者。 | Agent 是否可能接触持久数据？数据损失或恢复代价真实存在时值得加入，不接触数据的主机不需要。 |
| [systemd 资源限制](../templates/optional/systemd-resource-limits.md) | 重负载任务使用用户级 systemd scope/service 和选定的内存、交换限制。 | Linux `systemd --user` 是否可用？是否运行内存密集任务？需要为系统保留多少余量？不能自行编造固定数值。 |
| [Windows Shell](../templates/platform/windows-shell.md) | PowerShell/运行时识别、LiteralPath、退出码、单 Shell 写入和 Unix-first fallback。 | Agent 是否实际运行在 Windows native，用户是否希望这些限制全局常驻？检测到 Windows 只代表相关，不代表已批准。 |

### Windows 选项逐条影响

| 规则 | 对开发的影响 |
| --- | --- |
| Shell 行为相关时确认 Windows native 或 WSL，并报告真实 PowerShell 路径与版本。 | 命令选择服从真实运行时，不混淆 WSL、alias 和 PowerShell 版本。 |
| 优先实际可运行的 `pwsh -NoProfile`，仅在必要时使用 Windows PowerShell 5.1。 | 获得现代语义，同时保留旧模块所需路径。 |
| 不假设 `pwsh` 标准路径。 | 避免 alias 存在但当前环境不能执行时重复失败。 |
| 文件写入保持在一个 Shell 中。 | 减少 PowerShell、cmd、Bash 和 WSL 之间的引号、路径和变量损坏。 |
| 使用 `-LiteralPath`、检查 `$LASTEXITCODE` 并保留 `stderr`。 | 特殊路径和外部程序失败保持可观察。 |
| 复杂可复用逻辑写入范围明确的 `.ps1`，任务脚本及时清理。 | 可复用逻辑更易维护，又不留下临时工具。 |
| 确有收益时才让 Unix-first 工作使用 Git Bash 或 WSL。 | Unix-first 项目保留自然工具链，同时避免习惯性混用 Shell。 |

## 部署时怎样选择模块

1. 读取最小核心，只读检查真实主机和现有全局 `AGENTS.md`，识别冲突。
2. 排除明显不相关的模块，不因为文件存在就展示一份通用问卷。
3. 对剩余候选项，用通俗语言说明行为、收益、代价、前提和推荐意见。
4. 让用户选择模块；检测和推荐都不等于批准。
5. 展示准确的合并 diff 和模块清单，获得确认并创建可恢复备份后再写入。
6. 验证核心和已选模块各出现一次，未选模块不存在，参数占位符已解决，原有本机规则仍然保留。

## Workspace 模块保持独立

主机全局部署不得顺便安装项目工作流。持续文档、实验记录和 Robotics 验证是 [templates/workspace/](../templates/workspace/) 下互相独立的选项，只能在目标仓库内部署。详见 [Workspace 持续文档工作流](workspace-continuous-documentation.zh-CN.md)。

## 维护方式

模板和模块文件是 Agent 实际执行的指令，本文负责解释影响。核心或模块规则变化时，应在同一次修改中更新本说明及其英文版本。不能因为某位用户在所有主机上都选择一项个人偏好，就把它提升为公共核心。
